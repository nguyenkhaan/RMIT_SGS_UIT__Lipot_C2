# Product and Engineering Specification

## 1. Objective

Build a local Next.js prototype that proves selective disclosure of rental application evidence through real TideCloak identities and tag-based end-to-end encryption.

The prototype is successful when the same ciphertext is handled by the application without giving every signed-in user, the application backend, or the administrator a universal way to decrypt it.

### Temporary mock-MVP mode

While TideCloak is repaired, the project may ship a temporary workflow MVP
using simulated identities and outcomes. It is a UI/API integration harness,
not a security proof: it must never claim encryption, real authentication, or
cryptographic selective decryption. By direct user decision, the UI does not
render a mock-mode label; the documentation remains explicit about this
limitation. The temporary boundary is replaced by the generated TideCloak
provider, token verifier, and E2EE helpers as soon as the service is available.

## 2. Assumptions

1. Docker CLI is available; Docker Desktop is optional.
2. The implementation machine has internet access during Tide enrolment and E2EE operations.
3. The official TideCloak initializer remains the supported starting point for Next.js.
4. The Phase 1 scaffold was generated with Node.js `v26.12.0`. Its lockfile resolves Next.js `16.4.2`, React and React DOM `19.3.1`, TypeScript `5.8.3`, `@types/node` `24.0.13`, and `@types/react` `19.1.8`. The root manifest deliberately keeps the generated compatible ranges for Next.js and React; `bun.lock` is the reproducible version source of truth.
5. Synthetic JSON/document previews are sufficient; no binary file upload is needed.
6. Four separate TideCloak accounts are available before recording the demo.
7. The seven-hour limit applies to implementation and demo preparation, so every optional feature must yield to the access-control story.
8. The mock MVP preserves stable identity, package, access-decision, and route
   contracts so a real TideCloak adapter can replace it without a UI rewrite.

## 3. User Stories

- As a tenant, I can create encrypted income and reference packages so that I do not send one complete dossier to every recipient.
- As Manager A, I can decrypt the income package intended for me and receive a clear denial for the reference package.
- As Manager B, I can decrypt the reference package intended for me and receive a clear denial for the income package.
- As an administrator, I can inspect operational metadata without reading either sensitive package.
- As a judge, I can see that the result comes from four real identities and real cryptographic permission checks rather than a UI role switch.

## 4. Technology Stack

| Concern | Decision |
| --- | --- |
| Application | Next.js with TypeScript, generated by `@tidecloak/nextjs` |
| Backend | Next.js App Router route handlers in the same project; no separate service |
| Package manager | Bun; commit `bun.lock`, not `package-lock.json` |
| Identity and IAM | TideCloak dev container |
| Authentication | TideCloak OIDC session through the generated SDK integration |
| Sensitive data | TideCloak browser-side tag-based E2EE |
| Authorization | Client/realm roles for UI plus E2EE realm roles for actual decrypt permission |
| Storage | In-memory or local prototype store containing ciphertext and safe metadata only |
| Styling | Use the generated baseline; add only what improves the demo story |
| Deployment | Local development environment |

In temporary mock-MVP mode, an ordinary App Router baseline may be scaffolded
with Bun while the official initializer is blocked. Tide's official tutorial
documents adding `@tidecloak/nextjs` to an existing App Router application, so
this is an intentional bridge rather than a permanent framework fork.

The generated scaffold is now present. The generated SDK dependency remains in
`package.json`, but this specification intentionally does not rely on a
specific TideCloak SDK API or version until the official existing-app
integration is verified against the running service.

The checked-in `tidecloak.json` is an empty placeholder, not an adapter. The
root layout must not mount `TideCloakProvider` until a downloaded adapter has
the server URL, realm, and client resource required by the SDK. This prevents
the SDK's default `/adapter.json` request while Phase 2.1 establishes the real
realm and client.

### Temporary mock replacement contract

The temporary bridge owns the typed `IdentitySession`, `IdentityGateway`,
`PackageProtectionGateway`, `SessionVerifier`, `RentalPackage`,
`PackageMetadata`, and `AccessDecision` contracts. Mock implementations may
return only simulated outcomes and must identify them as mock results. The real
integration replaces the identity gateway with the generated provider/redirect
flow, the server verifier with TideCloak token verification, and the protection
gateway with browser `doEncrypt` and `doDecrypt` calls. Until the swap is
verified, UI copy must not present any temporary outcome as authentication,
encryption, or policy enforcement.

For the approved temporary runtime, `POST /api/demo-session` creates an opaque,
HTTP-only local session for one of the four published demo identities and
`DELETE /api/demo-session` removes it. `GET /api/packages` and
`POST /api/packages/:id/access` verify that session on the server before
returning safe metadata or a simulated access decision. This is a swap seam,
not an authorization claim: real TideCloak replaces the session route with its
provider/session, verifies a token server-side, and makes the decrypt decision
at the E2EE boundary.

## 6. Target Project Structure

The generated project structure takes precedence. The target responsibility layout is:

```text
.
├── app/ or src/app/            # Next.js routes and layouts from the initializer
│   ├── api/                    # Token-verified ciphertext/metadata endpoints, if needed
│   ├── auth/redirect/          # TideCloak redirect route
│   └── ...                     # Role-specific demo screens
├── components/                 # Package cards, access results, active-identity display
├── lib/
│   ├── rental-packages/        # Domain data and serialization
│   └── tidecloak/              # Role/tag mapping and thin SDK adapters
├── public/                     # Generated silent-SSO assets, if present
├── docs/                       # SDD source of truth
├── AGENTS.md                   # Agent operating rules
├── docker-compose.yaml          # Local TideCloak service; password comes from the shell environment
├── tidecloak.json              # Adapter config only if safe for a public repository
└── package.json                # Actual commands and dependency versions
```

Do not reorganize generated TideCloak files only to match this example. Prefer a small, obvious change over a speculative abstraction.

Frontend and backend work stay in this repository and are delivered by vertical
feature slice. Lock the feature contract first, then UI and route/store tasks may
proceed in parallel. Join them at an integration checkpoint before starting the
next dependent slice.

## 7. Code Style

- TypeScript for application code.
- Domain names describe intent: `RentalPackage`, `PackageMetadata`, `AccessDecision`, `recipientId`.
- One function should perform one domain action.
- Keep TideCloak role and tag strings in one typed mapping.
- Return explicit access states instead of booleans that lose error context.
- Comments explain security intent or a non-obvious constraint, not the visible code.

Example style:

```ts
type AccessDecision =
  | { status: 'granted'; plaintext: string }
  | { status: 'denied'; reason: string };

async function openRentalPackage(
  rentalPackage: RentalPackage,
): Promise<AccessDecision> {
  // TideCloak is the enforcement boundary; the UI only presents its result.
  return decryptWithRequiredTag(rentalPackage);
}
```

## 8. Testing Strategy

### Mandatory manual acceptance

Run the full identity/package matrix from `requirement.md` using real TideCloak sessions. Every allowed and denied path is required before recording.

### Build-time verification

- Lint the application with the script generated or configured in `package.json`.
- Produce a successful production build.
- Confirm no secret or plaintext package appears in tracked files or console logs.
- In temporary mode, confirm the UI contains no claim that a test result is a
  TideCloak or E2EE result.

### Automated tests

Automate pure domain behaviour only if it does not threaten the seven-hour core demo. Good candidates are package serialization, metadata redaction, and tag selection. Do not mock E2EE and call that an integration test.

### Integration verification

The TideCloak integration is verified manually against the running dev container because its value is the real session, role, QEA, and Fabric interaction. Capture exact failures and update `tidecloak-integration.md` if the generated SDK differs from official docs.

## 9. Boundaries

### Always

- Use synthetic data.
- Encrypt in the authorised browser session before storing a package.
- Keep persisted sensitive payloads as ciphertext.
- Show the active identity and the access result.
- Test both the allow and deny path for every package.
- Update specification documents before changing agreed behaviour.

### Ask first

- Add a database, upload service, cloud host, or runtime dependency.
- Add automated administration through a service account.
- Change role names, tags, users, or the access matrix.
- Add multi-admin QEA identities beyond the four core demo users.
- Commit any configuration that might contain a client secret.

### Never

- Commit credentials, tokens, real PII, plaintext packages, or local TideCloak state.
- Give Admin a package decrypt role.
- Treat hidden UI as authorization.
- Fall back to mock auth/E2EE in the submitted demo.
- Present temporary outcomes as real TideCloak authentication, E2EE, or policy
  enforcement.
- Claim that revocation erases information already viewed.
- Claim that a one-admin QEA realm demonstrates multi-party approval.

## 10. Success Criteria

- [ ] TideCloak starts from a local dev container and the Next.js app signs in against it.
- [ ] Four separate accounts are visibly used; there is no role-switch control.
- [ ] Tenant creates two encrypted packages with different tags.
- [ ] Manager A succeeds only for Income Pack.
- [ ] Manager B succeeds only for Reference Pack.
- [ ] Admin sees metadata and fails to decrypt both packages.
- [ ] Stored or transported sensitive content is ciphertext.
- [ ] Denials come from the TideCloak/E2EE operation and are clearly presented.
- [ ] Revocation language and behaviour match `requirement.md`.
- [ ] Lint and production build pass.
- [ ] README challenge overview remains under 300 words.
- [ ] The complete story can be recorded in under two minutes.
- [ ] The temporary MVP, if used, is documented only as an integration harness
  and makes no real TideCloak/E2EE claim in the UI.
